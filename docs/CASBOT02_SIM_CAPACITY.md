# Casbot02 接触 / 约束容量验证

2026-10-24，RTX 4090 D，当前 40 条清洗 LAFAN1（441,093 帧），4096 个环境。结论：**96/320 通过本次参考帧、动态压力与真实训练短测，可作为当前配置的减小候选。正式训练默认值仍为 128/500，本次只在验证进程内覆盖。**

## 测试与结果

| 测试 | 128/500 | 96/320 |
|---|---:|---:|
| 全部 441,093 个参考帧的最大约束数 / 环境 | 207 | 207 |
| 有效策略，4096 环境 × 1000 控制步的最大约束数 | 256 | 192 |
| 独立种子随机动作，4096 环境 × 1000 控制步 | 未重复 | 219，79,859 次重置 |
| 世界模型 + actor/critic 实际训练 | 本轮未重复 | 100 次外层更新，290 环境步，最大约束数 216 |
| batch 4096、4096 环境的追加训练检查 | 本轮未重复 | 首次外层更新后 CUDA OOM，未通过 |
| 接触池、约束行与稀疏 Jacobian 容量溢出 | 已测项均为 0 | 已测项均为 0 |

动态测试保留动作执行噪声、观测噪声、重置噪声、域随机化与回报重置采样，保持物理自碰撞和原终止条件；使用旧有效 `ckpt_0280000.pt` 做策略压力测试。实际训练从头开始，使用当前论文对齐版本、batch=2048、H=32、WM k=8，所有参数和已记录标量有限。测试权重保存在独立 `logs/capacity_96_320_training/`，仅用于验证。

两种容量的**参考帧接触峰值、最大约束数和约束数直方图完全一致**。闭环测试不是逐位等价对拍：并行物理的数值差异会随时间累积，不应通过这两条轨迹的平均奖励比较训练质量。

候选设置的接触缓冲是共享的 `96 × 4096 = 393,216` 个槽位；已测接触池最高 73,155（18.6%），宽相候选对最高 89,670（22.8%）。`njmax=320` 则是每环境的硬上限：候选测试最高 219；基线策略测试曾达到 256，仍低于 320。只监测总接触数不足以确认每环境约束安全。

## 显存

相同参考帧审计场景、独立进程，`nvidia-smi` 报告的进程显存占用：

| 配置 | 进程显存 |
|---|---:|
| 128/500 | 10,014 MiB（9.78 GiB） |
| 96/320 | 7,806 MiB（7.62 GiB） |
| 差值 | **2,208 MiB（2.16 GiB）** |

其中约束填充容量 `njmax_pad` 从 512 降至 320。完整 4096 环境 / batch 2048 的候选训练进程占用约 18,866 MiB（18.42 GiB），不含桌面及其他进程。

### batch 4096 追加实测

同日将策略 batch 提高到 4096，保持 4096 环境、96/320、H=32、当前论文对齐配置及全部清洗数据；计划运行 100 次更新，实际在首次外层更新后的下一次 Warp 仿真图启动时发生 **CUDA out of memory**。本次未通过，不能作为可运行配置推荐。

每秒一次的 `nvidia-smi` 采样记录：

| 项目 | 观测值 |
|---|---:|
| 训练进程显存最高观测值 | 21,750 MiB（21.24 GiB） |
| 整卡已用显存最高观测值 | 24,005 MiB（23.44 GiB） |
| 最低剩余显存 | 56 MiB |
| 计算阶段整卡 GPU 利用率最高值 | 98% |
| 启动前整卡已用显存 | 2,247 MiB（含桌面等进程） |

内存统计包含首次编译，1 秒采样可能漏掉更短的峰值。失败前最大约束数为 188，接触池、约束行及稀疏 Jacobian 容量溢出均为 0；这里的失败是 GPU 显存耗尽，而非 `nconmax/njmax` 不够。异常位于下一次仿真调用，不能仅按报错堆栈把显存压力归因于仿真缓冲：策略 batch 增大后的计算图、激活与分配器占用会共同挤占后续仿真的空间。

常规入口保留已通过的 **4096 环境 / batch 2048**。上述是只使用 96/320 的结果；后续缩缓冲与缓存释放诊断见下一节。正式参数尚未修改。原始 [失败报告](../outputs/casbot02_hardware/capacity_96_320_training_batch4096.json) 与 [逐秒显存记录](../outputs/casbot02_hardware/capacity_96_320_training_batch4096_gpu.json) 已保存。

## 继续缩小：64/288、48/288、32/288

三档均在 **4096 环境**下重新扫描全部 441,093 帧，接触峰值、最大约束数 207 和约束数直方图与 128/500 基线一致。仿真审计进程占用分别为 5,758、4,702、3,678 MiB。`njmax=288` 给历史已观测的 256 条约束保留 32 条余量。

但仅缩小缓冲，batch 4096 仍不能正常持续训练：

| 缓冲 | 仅减缓冲的实际结果 | 已完成外层更新 |
|---|---|---:|
| 64/288 | 下一轮 Warp 图启动时 CUDA OOM | 1 |
| 48/288 | 下一轮 Warp 图启动时 CUDA OOM | 1 |
| 32/288 | 下一轮 Warp 图启动时 CUDA OOM | 2 |

这些失败前的接触/约束数组溢出均为 0。32/288 失败时 PyTorch 活跃张量约 3.81 GiB，但分配器保留约 19.01 GiB；想象反传期间活跃张量峰值约 17.68 GiB。缩减仿真缓冲并没有消除想象训练本身的峰值和分配器缓存压力。

### 隔离的缓存释放诊断

验证脚本新增可选 `--trim-torch-cache`：每次外层学习更新完成、回到下一轮数据采集前，调用一次 `torch.cuda.empty_cache()` 释放闲置缓存。100 次更新中调用 99 次，不在每个物理子步执行。该处理只回收未使用的 Torch 缓存，不改变 batch、H、loss、梯度裁剪、学习率、奖励或 TF32；**目前只存在于独立验证脚本，未接入正式 `sm-train`**。

| 缓冲＋缓存释放 | batch / 环境 | 实际训练 | 进程显存最高观测值 | 整卡最低剩余显存 |
|---|---|---|---:|---:|
| 64/288 | 4096 / 4096 | 100 次更新通过 | 21,742 MiB（21.23 GiB） | 800 MiB |
| 48/288 | 4096 / 4096 | 100 次更新通过 | 21,642 MiB（21.13 GiB） | 239 MiB |

两组参数和已记录标量均有限，训练期间最大约束数均为 240，无接触池、约束行或稀疏 Jacobian 容量溢出。两组活跃张量峰值均为约 17.68 GiB，说明进一步减少这些缓冲对完整训练峰值的帮助有限。桌面等进程占用在测试间波动，不能把两次最低剩余显存的差异全部归因于缓冲参数；1 秒采样也可能遗漏瞬时峰值。

48/288 还完成了额外的两组 4096 环境 × 1000 控制步压力测试：旧有效策略最大约束数 204，随机动作最大约束数 224（84,196 次重置），接触池、约束行及稀疏 Jacobian 容量溢出均为 0。

缓存释放有明显开销：两组各累计约 31.2 秒，总测试墙钟约 134–136 秒；这不是与 batch 2048 的严格吞吐对照。**通过 100 次更新证明该诊断组合可运行，但剩余显存很紧，不能视为已验证长期稳定训练。** 常规训练仍使用已验证的 batch 2048，或另行实现并验证降低反传峰值的方案。

参考姿态中单个世界最多出现过 66 个接触。48/288、32/288 在本次 4096 并行环境中利用了共享接触池，不能据此将相同 `nconmax` 直接用于单环境 play；正式接入时应分别验证训练和评测容量。默认配置仍为 Casbot02 128/500、G1 35/250。

复查缓存诊断（更换新的输出名；这是短测脚本）：

```bash
env -u PYTHONPATH uv run python scripts/validate_sim_capacity.py \
  --mode train --nconmax 48 --njmax 288 \
  --num-envs 4096 --batch-size 4096 --iterations 100 --trim-torch-cache \
  --out outputs/casbot02_hardware/capacity_48_288_training_batch4096_trim_repeat.json
```

## 如何监测

正式配置的 `QuietSimulationCfg` 关闭了每步溢出 printf，本次没有用“没看到 warning”作为通过标准。独立脚本包装 `sim.step()` 和 `sim.forward()`，在每个 200 Hz 物理子步及重置后的 forward 读取：

- 全局 `nacon`、`ncollision` 与共享 `naconmax`。
- 每环境 `nefc` 与 `njmax`。
- `NEFC`、`NJMAX_NNZ`、`BROADPHASE`、`NARROWPHASE` 标志，并跨子步保留，避免重置清除证据。

`ITERATIONS`、`LS_ITERATIONS` 另行报告；原基线也出现这些求解器迭代上限标志，它们不等于接触/约束数组溢出。本次没有改变原有 10 次 solver / 20 次 linesearch 设置。

复查命令（更换输出文件名，训练模式也要使用新的输出名以避免覆盖同名 run）：

```bash
env -u PYTHONPATH uv run python scripts/validate_sim_capacity.py \
  --mode audit --nconmax 96 --njmax 320 \
  --out outputs/casbot02_hardware/capacity_96_320_reference_repeat.json

env -u PYTHONPATH uv run python scripts/validate_sim_capacity.py \
  --mode train --nconmax 96 --njmax 320 --iterations 100 --batch-size 2048 \
  --out outputs/casbot02_hardware/capacity_96_320_training_repeat.json
```

默认数据目录为 `data/npz/lafan1_casbot02_codex`。结论只覆盖当前模型、地面、数据与已测状态；长训进入其他接触状态后仍应监测容量。原始报告及负对照结果索引见 [汇总 JSON](../outputs/casbot02_hardware/sim_capacity_validation.json)。
